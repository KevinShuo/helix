# 本地 27B 思考与 DeepSeek 测试生成实测

后续已完成 [DeepSeek 开启思考、16K 预算的完整 6 例复测](deepseek-thinking-16k-full/report.md)：
6/6 通过、18/18 缺陷检出、中位生成 23.2 秒。下文保留最初轮次和较小预算补测的原始结果。

日期：2026-11-15。6 个固定目标，C、C++、Python 各 2 个；每个目标
3 个预置缺陷，共 18 个。两个首轮模型各调用一次，不重试、不手改生成测试。
全部使用真实编译器、vcpkg GoogleTest、pytest，原始输出和失败均保留。

本轮结论：**DeepSeek 非思考生成明显更快；两种模型都出现了会影响实际使用的
错误，不能只凭开启思考或测试数量判断质量。** 本地模型在这组任务的首轮完整
流程中多完成一个任务；仅看独立运行的测试代码，两者各有 4/6 可运行。
样本很小，不能推断一般准确率。

## 首轮和环境复核

实测发现 Windows MSVC 默认代码页 936 与生成的中文 UTF-8 注释不匹配。
这会产生编译错误，甚至吞掉测试声明导致零测试。第一份本地 C 测试不改一字，
只增加 `/utf-8` 编译选项后，21 个用例全部通过。

因此保留两层结果：原安装环境的首轮结果，以及**同一份测试文件逐字节不变、
统一 UTF-8 编译的重放结果**。后者用来区分工具链问题与模型的代码/断言错误。

| 指标（每组 6 个目标） | 27B 思考 | DeepSeek 非思考 |
|---|---:|---:|
| 收到完整 HTTP 回复 | 5/6 | 6/6 |
| 通过生产输出校验 | 5/6 | 5/6 |
| 原安装环境直接编译/运行通过 | 3/6 | 1/6 |
| UTF-8 重放，仍严格执行生产验收 | **4/6** | **3/6** |
| 上述可用套件检出的缺陷／全部 18 个缺陷 | **12/18** | **9/18** |
| 另行只执行原始代码，绕过 JSON 包装问题 | 4/6，12/18 | 4/6，12/18 |

“检出／18”包含未运行任务的机会成本：严格流程实际分别运行了 12 个和 9 个
缺陷，均检出；未编译或未验收的任务不计为检出，不代表修复后的套件检测能力为零。
DeepSeek 的 Python 去重测试缺少必需的 `assumptions` 字段，严格流程拒绝；单独
取出原 `code` 执行则通过并检出 3/3。这项包装绕过仅列为诊断，没有加入严格成绩。

## 每个目标的结果和生成耗时

耗时从构建请求到收到并校验输出，不含模型加载、编译/执行、缺陷实验。
结果列采用 UTF-8 环境重放，生成代码没有人工改写。

| 目标 | 27B 思考 | DeepSeek 非思考 |
|---|---|---|
| C：parse_u16 | 66.5 秒；通过，3/3 缺陷 | 7.4 秒；缺少 C linkage，链接失败 |
| C：copy_prefix | 首轮连接失败，未收到输出 | 5.5 秒；通过，3/3 缺陷 |
| C++：merge_ranges | 106.5 秒；通过，3/3 缺陷 | 5.9 秒；gtest 宏参数写法导致编译失败 |
| C++：Quota::consume | 42.1 秒；一条预期值错误，原实现测试失败 | 4.2 秒；通过，3/3 缺陷 |
| Python：parse_port | 62.4 秒；通过，3/3 缺陷 | 4.0 秒；通过，3/3 缺陷 |
| Python：unique_by | 45.9 秒；通过，3/3 缺陷 | 3.3 秒；缺少 JSON 字段；原代码单独运行通过，3/3 |

成功收到 HTTP 回复的生成中位耗时：**27B 62.4 秒（n=5），DeepSeek 4.9 秒（n=6）**。
总生成时间分别为 323.4 秒与 30.4 秒；本地首轮缺失一个目标，不能把这两个总数
视为完成相同任务量的总成本。本轮本地模型额外加载耗时 **8.7 秒**。
普通编辑器使用时还可能有 9B 卸载和恢复开销，本轮没有测量该切换过程。

编译/执行时间另列在 [case-results.csv](case-results.csv)；原始阶段日志在每个
`result.json`，UTF-8 重放日志在 `utf8-replay/`。缺陷实验的重复构建不计入日常响应耗时。

## 生成质量的具体观察

- 本地 `parse_u16` 包含上下界、前导零、非法字符、NULL 和失败状态不变，oracle
  正确；生成 21 个用例，最大值和前导零场景有重复，存在压缩和参数化空间。
- 本地 `merge_ranges` 正确处理共享端点、相邻不合并、倒序和嵌套区间、输入不变；
  通过临时变量/字段断言避开了 gtest 初始化列表逗号问题。
- 本地 `Quota` 的解释写明 `consume(0)` 在耗尽后应成功，代码却在对应测试中写了
  `EXPECT_FALSE(q.consume(0))`。这条断言与公开契约及原实现冲突，不能把它改成
  业务代码修改任务，也不能为了获得通过率偷偷调整预期值。
- DeepSeek `parse_u16` 没有在 C++ 测试中用正确的 `extern "C"` 包含 C 头文件；其
  assumptions 还错误地把跨语言链接交给 CMake，尽管提示词明确要求正确 C linkage。
- DeepSeek `merge_ranges` 在多个 `EXPECT_EQ` 的第二个参数中直接写
  `Ranges{{1, 5}}`，没有括号保护初始化列表逗号，触发宏展开编译错误。边界思路
  基本正确，但这份原始代码不可执行。
- DeepSeek `copy_prefix` 和 `Quota` 的可运行套件覆盖了本次所有预置缺陷；Python
  两个套件也有正常/边界/异常与状态或调用次数检查。`unique_by` 的一条测试说明
  写“元组作为键”，实际回调返回整数键，属于说明不够准确。
- DeepSeek `copy_prefix` 的故障诊断有内存安全问题：全 `X` 填充的缓冲区在
  “遗漏 NUL”缺陷下没有界内终止符，`EXPECT_STREQ`、`strlen`、`std::string(dst)`
  会越界读取。保存的日志中，10 字节数组的 `strlen` 返回了 49，并打印出调试
  栈填充值。本次仍保留观察到的 3/3 检出，因为安全的单字节断言也独立发现了
  该缺陷；这不能据此认定测试套件在被测实现有缺陷时也安全。应改用有界比较，
  并先验证终止符再进行字符串操作，本实验没有手动改写该模型输出。
- 两组 Python 有效代码都验证了端口上下界、ASCII 限制、空白和符号，以及去重的
  稳定顺序、key 调用次数、异常传播。没有靠 mock 掉被测函数获得通过。

## 单独补测，排除在首轮统计之外

1. 本地 `copy_prefix` 在新服务和新进程中补测一次：**61.9 秒**，收到完整代码，
   但先按 C++ 包含头文件，又追加同名 `extern "C"` 声明，产生 C2732 linkage
   冲突，未通过编译。首轮连接失败原因没有进一步定位；补测没有替换首轮记录。
2. DeepSeek 对首轮失败的 C 解析、C++ 区间合并、Python 去重开启思考补测：
   **21.9／23.3／23.6 秒**，三次均 `finish_reason="length"`，输出恰好达到
   4096 completion tokens，严格流程拒绝，未运行代码。
3. 这三次思考补测只能说明当前总输出预算不足。当前实现给本地思考额外预留
   2048，而 DeepSeek 思考与最终输出共用 4096。需要适配预算后再评估思考模式
   代码质量，不能从截断结果推断模型能力，也不能宣称开启思考已经解决上述错误。

## 对功能设计的建议与本次修复

保留双模型路线：需要离线时使用本地 27B；响应速度优先时可用 DeepSeek 生成
草稿。两种模式均应保留预览、真实编译/运行、失败诊断及断言审查。

优先改进方向：C 头文件 linkage 处理、gtest 宏逗号检查、JSON 字段完整性检查，
以及 DeepSeek 思考预算适配。本地输出可以通过参数化和去除重复用例缩短；按
本轮约 38 token/秒估算，6144-token 极限输出可能超过现有 120 秒超时。

本次已修复确定的编码接入缺陷：MSVC `/utf-8` 通过 SOURCE 属性仅应用到新生成
文件，并指定 TARGET_DIRECTORY，兼容复用已有测试 target，保留其他手写文件的
编译编码。中文注释回归在修复前失败，修复后的本机 GTest、已有 target、
FetchContent 三个真实构建场景全部通过。没有修改模型生成的断言、业务源码或
用户的默认模型/思考开关。

最终默认测试：151 项单元测试和 2 项 doctest 通过；12 项 opt-in 单测及 1 项
doctest 忽略。评测脚本通过 Ruff lint/format 和 Python 编译检查。

# 本地行内补全的正确建议与错误灰字

在同一台 Core Ultra 7 155H 笔记本上，新旧 hx 都使用 llama.cpp CPU 和 Qwen2.5-Coder-3B-Instruct Q4_K_M。用独立的真实编辑器窗口输入缺口前的最后一个字符，最多等 5 秒，接受灰字、保存，再运行 Python 或 C++ 断言。两组样例各跑一遍，新增题先跑旧版，原题先跑新版。计时从最后一次按键到屏幕显示灰字。未显示建议的题单独计数。

| 测试集 | 版本 | 正确 | 错误 | 未显示 | 显示建议的中位耗时 |
|---|---|---:|---:|---:|---:|
| 原有 42 题 | 旧 | 24 | 17 | 1 | 1065 ms |
| 原有 42 题 | 新 | 23 | 9 | 10 | 1027 ms |
| 新增 18 题 | 旧 | 5 | 13 | 0 | 1147 ms |
| 新增 18 题 | 新 | 8 | 4 | 6 | 988 ms |

旧版显示了 59 条建议，29 条通过断言。新版显示了 44 条，31 条通过。已显示建议的正确比例从 49.2% 变为 70.5%，全部 60 道题中实际得到正确建议的比例从 48.3% 变为 51.7%。新增题涵盖字典操作、字符串处理、窗口计数和容器算法，18 个参考答案均已执行通过。这些人工样例无法代表用户在真实项目里接受灰字的比例。[逐题结果](editor-results.csv) · [新增样例及断言](additional-fixtures.json)

原题中，旧版正确补出的 64 位掩码在新版被隐藏。新版也隐藏了 8 条原先错误的灰字。新增题中，去除行尾换行符、取出并删除字典项、判断有序这 3 条从错误变为正确。例如字典题要求键缺失时返回 None，旧版用了 get，新版用了 pop。高置信度的逻辑错误依然存在，例如用普通整数相加后再除以二求平均值，仍可能溢出。

## 选择依据

保守的本地缺口补全在同一次请求中读取输出 token 的对数概率。笔记本模型包设置 `min-gap-confidence = 70`，按生成代码 token 概率的几何平均值筛选建议。该指标反映模型选词的确定程度，程序行为是否正确由断言单独检验。下一行预测和语言服务器直接确定的变量名继续走各自原有的路径。

在固定文件名的模型请求测试中，原提示词得到 27 条正确、13 条错误。加长契约提示并替换示例后得到 25 条正确、17 条错误，因此保留原缺口提示。原提示配合 70% 的 token 概率门槛，得到 26 条正确、6 条错误。对短行中紧靠成员访问符的缺口，改为让模型输出完整的一行，编辑器核对已经输入的接收者和后续代码，再提取缺失部分。阈值比较及成员提示选择用到了这批人工样例，表中数据属于本地回归测量。
## 对 16 个未显示建议的缺口做复测

从上述 60 题选取新版未显示灰字的全部 16 题。用已安装的 hx 和同一个本地 3B 模型，在独立窗口分别以 65 和 70 的门槛重放输入，每题最多等 5 秒。另在模型请求层用同样的前后文测试 llama.cpp 原生填空，经过 Helix 的清理与语法检查，再离线应用 70 的门槛。每组每题运行一次，并用原断言评分。

| 方法 | 正确 | 错误 | 未显示 |
|---|---:|---:|---:|
| 当前 hx，门槛 70 | 0 | 0 | 16 |
| 当前 hx，门槛 65 | 1 | 1 | 14 |
| 原生填空，门槛 70 | 5 | 5 | 6 |

降低门槛后，排序去重题通过，查找首个匹配项的建议仍未通过。原生填空找回了 64 位掩码、闭区间相交等正确建议，也给出了错误的取模和字节转换。原生填空单次请求中位耗时为 840 ms；若作为串行重试，这段时间会叠加在首轮请求之后。该耗时只覆盖模型请求。三组结果仅描述这 16 个上轮留白的缺口。

## 函数实参、条件和换行的首条灰字

在同一台笔记本和同一份 3B CPU 配置上，旧版和候选版各打开一个独立的 hx，在每种场景中各输入两次。从发出最后一次按键开始轮询屏幕，最多等待 5 秒。出现灰字就接受、保存并核对整个变量名，Python 函数体另外以负数、零、正数和小数调用验证。C++ 文件使用已经启动的 clangd。

| 编辑位置 | 旧版两轮 | 候选版两轮 |
|---|---|---|
| 函数第一个实参，补全 `payload_size` | 648、662 ms | 48、61 ms |
| `if` 条件，补全 `ready_count` | 两轮未显示 | 62、55 ms |
| 函数第二个实参，补全 `right_value` | 首轮未显示，次轮在 692 ms 给出错误的 `righight_value` | 62、62 ms |
| Python 的 `def square(number):  # Return the square of number` 后按回车 | 两轮未显示 | 523、1090 ms，均生成 `return number * number` |
| Python 的 `return 0` 后按回车 | 两轮未显示 | 两轮未显示，调试日志均记录该位置没有触发预测 |

在应当给出建议的八次输入中，200 ms 内出现正确灰字的次数从 0 次变为 6 次，均为语言服务器能够唯一确定的变量名。Python 函数体两次都需要模型生成。各位置仅测两次。

再以同一套真实编辑器流程重跑原有 60 道代码缺口题。上一版和本次均为 31 条正确、13 条错误、16 次未显示，200 ms 内给出正确建议均为 0/60。已显示建议的中位耗时从 1014 ms 变为 1078 ms，P90 从 1663 ms 变为 1716 ms。两次测量中，有符号整数向上取整从错误变为正确，判断有序从正确变为无法编译。后者生成了需要两个参数的 lambda，而 `std::all_of` 每次只传入一个元素。每个版本每题仅跑一遍。
